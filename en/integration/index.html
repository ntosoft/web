Integration & API

One stable interface for your software and behind it complete communication with national registries, insurer services and other systems. This page describes what an integration consists of and how we work with the individual interfaces.

INTEGRATION

An integration layer between your system and national services

Behind a single interface run adapters for individual protocols, certificate management, message queues and an audit log. A change in a national service specification is handled in one place instead of in every application.

SOLUTION COMPONENTS

What an integration solution consists of

An integration is not a single API call. It is a set of components that together ensure secure and traceable communication.

Client modules

Libraries and services for specific interfaces: patient lookup, reporting, electronic prescription, document sharing. They are generated from OpenAPI and WSDL specifications and validate data before sending.

Access and certificate management

A secure store for client certificates, validity tracking, expiry warnings and controlled renewal without interrupting operations.

Mapping and validation

Conversion between your system's internal data model and interface formats. Checks of code systems, mandatory fields and rules before sending so errors are resolved at the source.

Queues and retries

Messages are first stored safely and only then sent. If a service is unavailable they are delivered later, in the correct order and without duplicates.

Monitoring and audit log

An overview of what was sent, with what result and by whom. Availability and latency metrics, error alerts and records for inspection and dispute handling.

Test environment and tooling

Simulators of national services for development without depending on external systems, regression test suites and preparation of material for verification with operators.

SECURE CONNECTIVITY

Authentication and secure communication

Client certificates (mTLS)

National services authenticate the facility with a certificate as part of the TLS connection. We keep certificates in a secured store, monitor their validity and prepare renewal ahead of time.

Identifying the requester

Every request carries the provider, the staff member and the purpose of processing, so the service knows who is retrieving data and why.

OAuth 2.0 and OpenID Connect

For our own API and connected applications we use short-lived tokens with permission scopes and single sign-on.

Overload protection

The gateway rate-limits requests and protects both the national interfaces and your systems from accidental flooding, for example after a client bug.

IDENTIFICATION

Identifying patients and providers

Data exchange between systems depends on reliable identification. Our layer works with the identifiers used by the national infrastructure and does not pass personal data where a meaningless key is enough.

IdentifierMeaning
RIDDepartmental patient identifier. It is meaningless, carries no personal data and serves as a common key for data exchange.
DRIDTemporary RID for offline work, connection outages or a person not yet identified. It is later assigned to a permanent RID.
AIFOAgenda-specific identifier of a natural person from the base registry system. Used only where the agenda requires it.
IČZ / IČPIdentification number of the healthcare provider. Together with the staff identification it determines who submits a request.
WORKFLOW

Request lifecycle

  1. Validation

    Input data is checked against schemas and code systems.

  2. Identification

    The patient is looked up or matched and an identifier is obtained.

  3. Mapping

    Data is converted to the format and code systems of the target service.

  4. Delivery

    The request is sent over a secured connection with a unique identifier.

  5. Response

    Status, warnings and errors are evaluated and returned in a clear form.

  6. Audit

    We record who did what, when and why.

ERRORS

Error states and retries

StatusMeaningLayer behavior
200Request processed.The result is stored and the event is written to the audit log.
400Invalid data.No retry. The error is returned with a field description.
401 / 403Missing or insufficient permission or certificate.No retry. An administrator is alerted; certificate validity and role are checked.
404Record does not exist.No retry. Evaluated in context, for example by creating a new record.
409State conflict or duplicate.No blind retry. The current state is fetched and a merge is decided.
429 / 5xxTemporary service outage or timeout.Retry with increasing delay. After the attempts run out the message moves to a dead-letter queue and an administrator is notified.
TYPICAL SCENARIOS

What it looks like in operation

Patient admission at a practice

Reception enters the patient's details. The integration layer verifies the provider, matches the patient in the master registry and returns an identifier that is stored in the record. If the service is unavailable the system creates a temporary identifier and completes the matching in the background. Every step is written to the audit log.

Reporting from a laboratory or ward

Once a result is confirmed the system assembles a report from the documentation data, checks code lists and mandatory fields and sends it to the relevant registry. Success is recorded against the case. A conflict response on repeated reporting leads to fetching the current state and merging, not to blind repetition.

Electronic prescription from issue to dispensing

The physician issues a prescription, the module signs it with a certificate and sends it to the central repository. The system tracks the prescription state so the practice can see whether it was dispensed or cancelled. A procedure is ready for outages that lets the physician carry on working and send the prescription later.

CALL EXAMPLES

What calls to the public ÚZIS API look like

The examples are based on the publicly available documentation of the ISIN interface (API V2, base address api.uzis.cz/v2). Path and field names follow the documentation, values are fictional. The shortened examples are for illustration and do not replace the operator's current documentation, which defines access conditions and authentication.

1. Patient lookup

A query by given name, family name and date of birth. The pcz parameter identifies the workplace submitting the query. The documentation also offers lookup by birth number, foreign insured person number, document number and agenda identifier.

# GET
curl -G https://api.uzis.cz/v2/pacienti/VyhledatDleJmenoPrijmeniDatumNarozeni \
  --data-urlencode "jmeno=Test" \
  --data-urlencode "prijmeni=Priklad" \
  --data-urlencode "datumNarozeni=1980-01-01" \
  --data-urlencode "pcz=123"

2. Recording a vaccination

One method both creates and changes a dose: without the id field a dose is created, with id it is updated. The interface rejects, for example, a duplicate vaccination of the same patient on the same day or a date in the future. Only the workplace that created a record can view and delete it.

3. Infectious disease report

A method for creating a new report. Checks cover code list links, duplicates by the combination of patient, diagnosis and date, and the workplace's permissions. The response contains the report number and a description of the request status. Status codes 200, 403, 404 and 409 correspond to processing, missing permission, a record not found and a conflict or duplicate. The path is shortened in the example.
